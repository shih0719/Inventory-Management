# ADR 0001：AP（序號品）不保留變更歷史

- 狀態：Accepted
- 日期：2026-05-05

## 背景

新增「序號品（AP）」實體後，每一台 AP 的 `status`、`sold_to`、`project_case` 等欄位會隨業務流程被修改（出貨、退貨、誤標修正）。

CONTEXT.md 對 Transaction 的設計原則明確規定：

> 「Transaction 是不可變的歷史紀錄——商品的當前數量是異動累積的結果，但每筆異動都留痕。」

這條原則只規範 Product 的數量變動，未涵蓋 AP 個體層級的狀態變更。AP 是否要比照辦理需要決定。

## 決策

**AP 的所有欄位變更採直接 UPDATE，不寫入任何歷史紀錄表。** 僅靠 `updated_at` 時間戳反映「最後一次被改動的時間」。

具體影響：

- 不新增 `ap_events` 之類的歷史表
- AP 變更**不**寫入既有 `transactions` 表
- 一台 AP 從 `in_stock` → `sold` 給客戶 A → 退回 → 再 `sold` 給客戶 B 後，資料庫只會看到「目前 sold 給客戶 B」，**先前持有過的客戶 A 不可考**

## 替代方案

- **方案 B：寫入既有 `transactions` 表**——需改動 transactions schema 加 `ap_id`，且 AP 狀態變更不對應 `quantity_change`，會讓既有邏輯尷尬。風險擴散到既有出/入庫流程。
- **方案 C：獨立 `ap_events` 歷史表**——審計最完整、不污染 transactions。實作量比 A 多一張表 + 一份寫入邏輯。

## 取捨

| 維度 | 採用方案 A 的後果 |
|---|---|
| 實作成本 | 最低，UPDATE 一張表搞定 |
| 與既有設計哲學一致性 | **違反**——Product 有完整異動歷史，AP 沒有 |
| 業務可追溯性 | 喪失——「這台筆電以前賣給誰」無法回答 |
| 未來補做的成本 | **高**——歷史一旦未記錄就回不來，未來只能從補做日起累積 |

選 A 的理由：目前業務只關心「現在這台在誰手上 / 屬於哪個案子」，沒有審計或歷史查詢需求；先以最小可行交付。

## 後續觸發條件

若**任一**情況出現，應重新評估改為方案 C：

- 業務開始需要查詢「這台 AP 過去曾賣給誰」
- 出現退貨爭議需要稽核軌跡
- 會計對接時要求 AP 的異動明細
